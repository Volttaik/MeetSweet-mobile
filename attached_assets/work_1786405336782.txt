UNDERSTAND THE SYSTEM BEFORE REVIEWING IT

The messaging architecture is based on a Chat Room, not the old Conversation system.

The old conversation architecture has been removed and must not be treated as the current architecture.

The fundamental structure is:

Chat Room
│
├── chatRoomId
│
├── User A
│   └── Context ID
│       └── Context Auth / Auth Tree
│           ├── Message A
│           ├── Message B
│           ├── Message C
│           └── ...
│
└── User B
    └── Context ID
        └── Context Auth / Auth Tree
            ├── Message A
            ├── Message B
            ├── Message C
            └── ...

The Chat Room is the permanent shared room.

The two users have separate contexts inside the same Chat Room.

---

1. CHAT ROOM

A Chat Room is the shared sandbox where two users communicate.

The Chat Room has a permanent:

chatRoomId

The mobile application does NOT invent authoritative Chat Room IDs.

When a user wants to message another user:

Mobile
→ sends participant information/request
→ Backend finds or creates the appropriate Chat Room
→ Backend generates/resolves chatRoomId
→ Backend returns the authoritative setup
→ Mobile opens the returned Chat Room

The client is the consumer of the Chat Room, not the authority that creates its persistent identity.

Check whether the code actually follows this architecture.

Look for:

- client-generated room IDs
- fake room IDs
- duplicate room creation
- local room creation that bypasses the backend
- legacy conversation logic
- hardcoded room identifiers
- incorrect participant handling

---

2. PARTICIPANTS

The Chat Room contains the users involved.

The two users must be identifiable using their user IDs.

The application should not depend on random navigation parameters such as:

name
username
avatar

as the authoritative identity of the participant.

Those may be UI information, but identity must ultimately resolve from the actual user/room data.

Check this carefully.

---

3. CONTEXT ID

Each participant has their own Context ID inside the Chat Room.

Example:

chatRoomId
│
├── contextId_A
└── contextId_B

Context ID is NOT:

- userId
- chatRoomId
- messageId
- Context Auth

It identifies that user's personal context within the shared Chat Room.

The two users therefore have:

User A → Context A
User B → Context B

Both contexts belong to the same Chat Room.

---

4. CONTEXT AUTH / AUTH TREE

Context Auth is also referred to as the Auth Tree.

This is extremely important.

Do not confuse:

Context ID

with:

Context Auth

Context ID identifies the user's context.

Context Auth is the message map belonging to that context.

Think of it as:

Context Auth
│
├── messageId_001
├── messageId_002
├── messageId_003
├── messageId_004
└── ...

Each message has its own authoritative message ID.

The Auth Tree allows the system to determine which messages currently belong to that user's context.

Therefore:

Chat Room
→ Context
→ Context Auth
→ Message IDs
→ Actual messages

The Auth Tree is what allows the two users to have different message visibility while sharing the same Chat Room.

5. DUAL CONTEXT BEHAVIOR

This is one of the most important things to verify.

User A and User B can have different versions of the same Chat Room.

Example:

Chat Room: ABC

User A Context:
Message 1
Message 2
Message 3
Message 4

User B Context:
Message 1
Message 2
Message 3
Message 4

If User A deletes Message 3 for themselves:

User A Context:
Message 1
Message 2
Message 4

User B Context:
Message 1
Message 2
Message 3
Message 4

The Chat Room itself still exists.

User B still has the message.

---

6. DELETE FOR ME

"Delete for me" affects only the requesting user's context.

The backend should update that user's Context Auth/Auth Tree.

The other participant must retain the message.

The mobile app should then synchronize its local representation accordingly.

Check that the implementation does not accidentally delete the message globally.

---

7. DELETE FOR EVERYONE

"Delete for everyone" affects both contexts.

Example:

User A Auth Tree
→ remove messageId_123

User B Auth Tree
→ remove messageId_123

The message should therefore disappear for both users.

Check:

- authorization
- message ownership rules
- both-context synchronization
- SQLite synchronization
- UI update
- server response handling

---

8. CLEAR CHAT

Clear means the current user clears their own Chat Room context.

It does NOT destroy the permanent Chat Room.

It does NOT necessarily destroy the other user's context.

Example:

Chat Room
│
├── User A Context → cleared
└── User B Context → unchanged

User A should no longer see their previous messages.

User B may still see them.

When User A later opens the Chat Room again, the same "chatRoomId" is reused, but User A's context remains cleared.

Verify that the code actually behaves this way.

---

9. DELETE CHAT / REMOVE CHAT FROM LIST

Deleting/removing a chat for one user must not destroy the shared Chat Room.

The Chat Room remains available.

The user's own context/list visibility can be removed.

When they message the same person again, the existing Chat Room should be reopened rather than creating a completely unrelated room.

Verify this.

---

10. BLOCK / UNBLOCK

Blocking does NOT delete the Chat Room.

The room becomes inactive/blocked.

Conceptually:

chatRoom.active = false

or the equivalent backend state.

Messages should not be allowed while the room is blocked.

Unblocking/reactivation should restore messaging.

Verify that the mobile app requests this operation from the backend rather than pretending to permanently own the state.

---

11. SENDING MESSAGES

The mobile app creates a request.

It does not become the authoritative message creator.

Expected architecture:

User types message
↓
Mobile creates request payload
↓
Backend validates request
↓
Backend creates authoritative messageId
↓
Backend stores message
↓
Backend updates appropriate context/auth structures
↓
Backend returns authoritative result
↓
Mobile updates SQLite/UI

Check whether the actual code follows this.

12. MESSAGE IDs

Every message must have a unique message ID.

The message ID is critical because operations such as:

- edit
- delete
- delete for everyone
- reaction
- reply
- synchronization
- local cache updates

Check for:

- missing IDs
- client-generated authoritative IDs
- inconsistent IDs
- temporary IDs never reconciled
- incorrect message-to-room relationships

Verify the entire chain.

28. DO NOT CONFUSE "PRESENT" WITH "WORKING"

Use these distinctions:

PRESENT

Code exists.

CONNECTED

Code is actually called.

FUNCTIONAL

The execution path produces the expected result.

VERIFIED

The implementation matches the architecture and has no obvious logical break in the inspected path.

A component may be:

PRESENT
but NOT CONNECTED.

A function may be:

CONNECTED
but NOT FUNCTIONAL.

A feature may be:

FUNCTIONAL
but ARCHITECTURALLY WRONG.

Your report must distinguish these.
